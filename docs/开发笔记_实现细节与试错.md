## 一、总览与设计骨架

路线设计是一条**从「量产的残卷」走到「唯一的原典」**的渐进链：

```
空白的书页 ──记录附魔──> 《如我所书》      ← 战斗向毕业装
      │
      └─ 十诫残卷 ×10 + 圣典 ──> 补全十诫 ──> 圣典解绑
                                             │
                          安息仪式 ──────────┘
                             │（冥界 · 需击败过使徒 · 七件稀有素材）
                             ▼
                        启示试炼（四波）
                             │（通关 → 带 NBT 的启示残卷 + 寂灭之星）
                             ▼
                        立约仪式（圣典 + 天启七印等）
                             ▼
                        圣约·原典（book 槽 · 效果未实现）
```

两条线的终点都是 book 槽，因此**互斥**（同槽只能戴一件）。

## 三、如我所书

**ID**：`yanscriptures:book_of_me`　**槽位**：book　**绑定**：戴上后只有创造模式能取下

### 3.1 基础属性（随记录附魔数量成长）

| 属性 | 数值 |
|---|---|
| 最大生命值 | 每个附魔 **+1** |
| 攻击力 | 每个附魔 **+1** |
| 幸运值 | 每个附魔 **+0.5** |
| 移动速度 | **+30%（独立乘区）** |

> 「已记录附魔恒定为 093」——**093 是崩铁致敬的设定值，不是强度门槛**。
> 收集数与属性脱钩，不要求玩家真去集齐 93 种附魔。

### 3.2 记录与回溯

- 按 **V** 记录当前状态（生命、饥饿、状态）
- 再次按 **V** 回溯，冷却 **180 秒**
- 状态记录消耗 10 种可用附魔

### 3.4 伤害相关的补充机制（战斗层）

- 攻击时若目标正在受玩家攻击，会叠加「灾厄印记」（由史诗饰品「灾厄」触发）
- 对戴书玩家的伤害拦截：负面效果在**施加阶段**即被拒绝（`MobEffectEvent.Applicable`）
- 免死：`LivingDeathEvent` 处有 **88%** 概率取消死亡并回满血
- 濒死保护：巡检层会在生命值 ≤0 且尚未进入死亡动画时救回（详见 §11.3）

### 3.5 战斗规则模块（BookOfMeCombatHandler）

这些是「毕业装特权」，按**通用语义**实现，不写死其它模组：

| 规则 | 实现依据 |
|---|---|
| 负面效果免疫 | `MobEffect#isBeneficial()` —— 非增益一律清除 |
| 无敌帧穿透 | 扫描目标类中名字含 `invul / iframe / cooldown / hurtcool` 的 int 字段与同步数据 |
| 生物伤害免疫 | 来源为 `Monster`（原版基类）的伤害一律取消 |
| 限伤穿透 | 临时抬高配置中字段名含 `cap / limit` 的数值项 |

### 4.3 残卷

**10 张十诫残卷 + 1 张启示残卷**，均 `stacksTo(1)`。

**第八诫的判据（2026-11-05，作者要求避免误伤）**：只有从**野生的战利品容器**里取出物品才算「偷」；
玩家自己摆放的箱子、木桶、潜影盒、漏斗等一律不触发。实现见
`CommandmentsHandler.onRightClickContainer` + `isLootContainer`：右键容器的那一 tick 记下
`WILD_INTERACT_TICK`，开界面时比对同一游戏刻，野生才记背包快照并在关闭时 diff。
「是不是野生的」走两条证据 —— 我们自己盖的 `YansWildLoot` 标记，或原版容器 NBT 里存在
`LootTable` 键（`RandomizableContainerBlockEntity#lootTable` 在 1.20.1 是 protected 字段，没有公开
getter，所以用 `saveWithFullMetadata()` 读，不反射别人的类）。别家自写战利品容器若不用原版那套
NBT，会被认成普通容器 —— 结果是「不诅咒」，不会误伤玩家。

稀有度（2026-11-05 作者定）：十张诫卷为**少见（黄色）**；**启示残卷**名字固定深红
（`ScriptureScrollItem.REVELATION_COLOR = 0xAA0000`，组件级颜色会盖掉稀有度颜色，
所以它注册时不设稀有度），与十诫残卷在物品栏里一眼可分。

| ID | 名称 |
|---|---|
| `scripture_of_shema` | 壹 · 示马残卷 |
| `scripture_of_silence` | 贰 · 无声残卷 |
| `scripture_of_thorns` | 叁 · 荆棘残卷 |
| `scripture_of_sabbath` | 肆 · 歇工残卷 |
| `scripture_of_rebellion` | 伍 · 悖逆残卷 |
| `scripture_of_blood` | 陆 · 血声残卷 |
| `scripture_of_harp` | 柒 · 挂琴残卷 |
| `scripture_of_shinar` | 捌 · 示拿残卷 |
| `scripture_of_tongue` | 玖 · 火舌残卷 |
| `scripture_of_vanity` | 拾 · 虚空残卷 |
| `scripture_of_revelation` | 启示残卷 |

**使用方式（十诫残卷）**：
- 必须佩戴《圣典·戒律》
- 对应诫条处于「已违逆」（有诅咒）且尚未补全
- 右键 → 补全该诫（写入 `Completed_n`、移除 `Curse_n`），消耗 1 张
- 补全后该诫**不再降罪**，祝福转为强化版

**启示残卷**：
- 普通：暗红色提示「等到那日子来临，举行盛大的仪式，这张残卷将揭示终结与新生。」
- 通过试炼（带 `TrialCleared:1b`）：亮白色「你已迈过了那审判，步入新天新地」

### 6.7 大书页（2026-11-05，作者要求）

**问题**：原版 tooltip 的高度由屏幕决定，一页只塞得下 5~12 行——十诫正文 30~50 行（`ScriptureOfCommandmentsItem.PAGE_SIZE = 5`）、圣约 12 条权柄 + 25 行典章、如我所书 30+ 行，翻一次要滚十几次。

**做法**：鼠标悬停在物品上，**按一下 Shift+Alt** 打开整屏书页。

| 项 | 内容 |
|---|---|
| 实现 | `client/BookPageScreen.java`（通用书页）+ `client/BookPageOpener.java`（`ScreenEvent.KeyPressed` 里判断悬停物品） |
| 尺寸 | 宽 `min(屏宽-40, 760)`、高 `屏高-40`；正文宽 720 上下，一屏约 25~30 行 |

| 行距 | 正文行高 10；**段落间最多留一行空行**（连续空行与首尾空行在 `init()` 里被压掉）。标题区高 30：标题 y+4、副标题 y+14、分隔线 y+25，正文从 y+30 开始（2026-11-05 修掉「横线穿过副标题」：原来标题区 26、副标题 y+17、线 y+22） |
| 覆盖 | 《如我所书》（`BookOfMeItem.FULL_DESCRIPTION`）、《圣约·原典》（权柄 + 典章明细两段拼接）、《十诫》（`ScriptureOfCommandmentsItem.fullLines`，强制显示触发条件与诅咒） |
| 不改动 | 旧的 tooltip 翻页逻辑全部保留（Shift 展开 + Shift+滚轮翻页），大书页只是多一个入口 |

**限制**：只在容器 GUI（背包、饰品栏）里生效——`getSlotUnderMouse()` 需要有槽位；在主世界盯着地上的物品看不会触发。纯客户端界面，不发网络包，也不影响拿起物品。

> ①影子被 `setCanceled` 之后仍会留下 20 刻 `invulnerableTime`，下一次横扫就进不了
> `LivingHurtEvent` → 每次处理影子伤害后 `shadow.invulnerableTime = 0`；
> ②玩家先命中本体时本体已有 10 刻无敌帧，影子转来的那一笔会被整个吃掉 →
> 转伤前把 `original.invulnerableTime = 0`，`finally` 里也留 0（不恢复旧值），
> 于是「先打本体」和「先扫影子」两种顺序都能落下两笔。
> 注意：`LivingEntity.lastHurt` 是 `protected`，外部类碰不到，能改的只有 `public int invulnerableTime`。
>
> 第三版（2026-11-02）改成「只补一笔、且去重」：`inSwing(attacker, original)` 判断玩家这一刀
> 是否同时罩住本体（`inflate(1.25)` 相交 + 朝向点积 > 0），命中影子且同时罩住时再转一笔；
> 但本体重扫自己那刀本来就打了一笔，于是同一刀会变三笔 —— 用
> `DOUBLE_SWING_TICK`（`Map<UUID, Integer>`）按 `attacker.tickCount` 去重，同一个 tick 只补一次；
> 再往下一层堵：补过之后 `DOUBLE_SETTLED` 记下「补给了谁」，`applyOutgoing` 见到
> 「同一 tick + 同一个本体」直接返回 0，把原版横扫紧跟的那一笔让掉。两处合起来，

  =「金太阳 / 银月亮 / 蓝地球」，基名 `entity.yanscriptures.celestial_orb` =「天体」
  （作者 2026-11-07：「三个星球依旧采用的是内部代码的名称，给他们改成中文」）。
  **颜色烘进顶点色**，不能用 `RenderSystem.setShaderColor`：`MultiBufferSource` 先攒顶点、实体渲染结束才统一提交，
  提交时 shader color 已重置成白色，第二版之前三颗球全渲染成灰白。
  接触判定 `CONTACT_RADIUS = 1.2`，按**生物碰撞箱**算距离（`mob.getBoundingBox().inflate(CONTACT_RADIUS)`
  再 `distanceToSqr(球心)`，只看球心点会把铁傀儡这类高大的怪判丢），同一颗球对同一只怪 `CONTACT_COOLDOWN = 10` 刻：
  地球 → 玩家随机正面效果 15 秒（同名再触发升一级，上限 IV）；月亮 → 20% 攻击力伤害 + 随机负面效果 15 秒，

  太阳 →  `150%` 攻击力，正午 `250%`、深夜 `50%`（同一相位线性插值）。

三条实现决策（都不是「随手一做」，写在这里备查）：

1. **附魔台 +20 没用 mixin，改用 `EnchantmentLevelSetEvent`。** 作者原话是「用 mixin 吧」，
   但本工程 2026-10-21 因为一次发布包启动崩溃把 mixin 整个摘掉（见 `build.gradle` 的注释），
   重新启用的风险是「开发环境能跑、正式包一进游戏就崩」。Forge 恰好留了
   `EnchantmentLevelSetEvent`（能直接改每行等级）与 `AnvilUpdateEvent`（能改经验消耗），
   用事件不碰别人一行字节码，是更稳的等价实现。
   代价：`EnchantmentLevelSetEvent` 里没有玩家信息，只能按「附魔台 8 格内有没有戴着的人」判断。
2. **《梦的解析》做成「梦游」状态，不是真维度。** 作者问过「写特殊状态还是真维度，你自行判断」，
   答「可以」。真维度要造 world、同步地形、把实体搬进搬出，一步出错就是存档级事故；
   状态方案把这些需求全做到，而且「梦里地形与现实 32 格一致」自动成立——人根本没离开现实世界。
   作者 2026-11-01 晚重述了完整设想（穿墙/飞行/无重力、生物像影子一样不动不掉血不燃烧不索敌、
   伤害总和 30% 梦醒结算、醒来回到入睡位置），全部按这条重写；冻结名单写在玩家
   `PersistentData` 的 `YanDreamMobs` 里而不是内存 Map，崩服重进也能把生物放出来。
   2026-11-01 深夜又修三处（作者实测）：①飞行改成**客户端每刻改 y 速度**，不再依赖
   `abilities.flying`（那套链路被同步/别的模组一碰就整条失效，表现为「钉在一个 y 上平移」）；
   ②解冻只还原 `YanDreamNoAiFlipped` 里记录的那批（否则本来没 AI 的训练假人会被“唤醒”）；
   ③`LivingDeathEvent` 拦截 + 每 5 刻回满血，兜住不走普通伤害事件的真伤技能。
3. **卦象/契约这类「持久状态」写在 `player.getPersistentData()`**，不用 NBT on item：
   换书、换附魔都不该让卦象归零，而死亡要清的东西（罪与罚层数、浮士德扣除）在
   `LivingDeathEvent` 里显式清。

`gui.yanscriptures.iching.{qian,kun,zhen,kan,li,gen}`；九本的 `.effect1/.effect2` 已从

### 七·五·一、材料档位带来的加成（2026-10-31 新增，同日改为「三条线各算」）

一条材料线记一档，一本书记三条线的档位（NBT：`YanPaper` / `YanInk` / `YanThread`），另记一项随机到的额外属性（`YanGradeAttr`）。

| 材料线 | Ⅰ | Ⅱ | Ⅲ | Ⅳ |
| --- | --- | --- | --- | --- |
| 纸 | 草纸 | 羊皮纸 | 至邪之笺 | 寂灭之笺 |
| 墨 | 墨水 | 血墨 | 不洁之墨 | — |
| 线 | 麻绳 | 金绳 | 龙筋 | — |

单条线的加成：**Ⅰ 0、Ⅱ +0.5%、Ⅲ +2.5%、Ⅳ +6%**（作者 m08532 定稿）。

三层叠加（作者 m08693 + m08876）：

1. **全属性** = 三条线相加，四条属性（攻击力 / 生命上限 / 护甲 / 移动速度）都加这么多；
2. 每条材料线出书时各自掷一项属性，**再把自己那一份加到那一项上**；
3. 换料 / 重掷只改被替换那一条线的档位与掷中的属性，另外两条原封不动。

以 Ⅳ/Ⅲ/Ⅲ 的书为例：

| 层 | 内容 |
| --- | --- |
| 全属性 | +11%（6 + 2.5 + 2.5）加到四项上 |
| 纸线（Ⅳ，掷中攻击力） | 攻击力再 +6% → 攻击力合计 +17% |
| 墨线（Ⅲ，掷中生命上限） | 生命上限再 +2.5% → 合计 +13.5% |
| 线线（Ⅲ，掷中护甲） | 护甲再 +2.5% → 合计 +13.5% |

> 作者最初给的是「Ⅱ +1% / Ⅲ +6% / Ⅳ +10%」，因为三条线会相加、饰品栏里每一本书都算，
> 按原数值叠起来太高，所以单线先压过一次；2026-10-31 作者定稿为上面的 0 / 0.5% / 2.5% / 6%。
> 要再调，只改 `MaterialBonus.PERCENT` 一个数组。

四项属性 = **攻击力、生命上限、护甲、移动速度**。三条线如果掷中同一项，那一项会叠三份（`perAttribute` 就是逐条累加）。

**独立乘区**：全部走 `AttributeModifier.Operation.MULTIPLY_TOTAL` —— 原版属性计算里最后一步的乘算层，乘的是「所有固定值加成算完之后的总数」。因此它不会被别的模组的 `ADDITION` 固定值冲淡，也不与事件层里那些「造成伤害 +X%」的加法混在一起；这是原版系统里能给出的最外层的乘算位置。

**饰品栏里的每一本书都算**（作者 m08405）：四本带档位的书就是四份相加，处理器按属性分别累计当前戴着的所有书，再往每一项属性上挂一条聚合修正器。

**显示方式**（作者 m08693、m09820）：物品介绍末尾是仿饰品模组的区块 ——

```
材料加成：
+11.0% 全属性（三条相加）
+6.0% 攻击力
+2.5% 生命上限
+2.5% 护甲
材料档位：纸 Ⅳ · 墨 Ⅲ · 线 Ⅲ
槽位：书
```

第一行是三条相加的总量，下面三行是每条线各自掷中的那一项（掷中同一项就会重复出现，读起来就是叠了三份）。

> 2026-11-01 修正：区块标题从「当装备在书籍栏：」改成「**材料加成：**」。
> 物品在书籍栏里时，Curios 自己会先加一段 `curios.modifiers.book`（中文译为「当装备在书籍栏：」）
> 列出**这件物品**本身的槽位属性（例如空白的书页的 `+10% 速度`，来自
> `BlankPageItem.getAttributeModifiers`）；材料加成是处理器直接挂在玩家属性上的，不归 Curios 管。
> 两个区块本来就该分开读，标题撞车才让人以为重复。

| 著书台（纸/墨/线三格 + 下半材料池 → 书） | `BookWritingTableBlockEntity.craft()` 出书时按三格材料打档 + 掷属性 |
| 锻造台「换料重铸」 | `MaterialUpgradeRecipe`：见下 |

### 设计约定

- **一件饰品 / 一个功能写一个文件**（2026-10-30 定）：九本名著当初被塞进同一个
  `ClassicBooksHandler`，一个文件一千多行、改一本要翻半天，还出现过「切片替换把整段复制一遍」
  的事故。以后新增的饰品与功能各自成文件，不再合并；已经写好的这几个保持现状不动。
- **跨模组材料一律走标签**：`yanscriptures:evil_essence`、`yanscriptures:unholy_blood`。

- **引用别家 id 的标签条目一律写 `{"id": "...", "required": false}`**（2026-11-01 血的教训）：
  1.20.1 的标签加载只要碰到一个不存在的 id，就会把**整份标签丢掉**——不报在代码里，
  只在你用的时候发现「怎么永远不生效」。《君主论》16 格光环就这么整个哑掉的
  （`minions.json` 里混了一个被诡厄巫法删掉的 servant id）。原版 id 可以写字符串，
  别家的、会随版本改名的，全部带 `required: false`。
- 三条线各有 `papers` / `inks` / `threads` 物品标签（`threads` 含麻绳 / 龙筋 / 金绳），著书台按标签认格子里放的是什么。
- 纸 / 墨 / 线一律**投料进锅**（`data/yanscriptures/cauldron/*.json`）：只数数量，扔的顺序不限，
  同一堆物品可以被一条配方吃掉多个（例如 16 根甘蔗能连出 4 次草纸）。
- 寂灭之笺的判定用信标存档数据里的 `Levels`（金字塔层数 > 0 即视为激活）；向下最多找 256 格，途中遇到 `isSolidRender` 的方块即视为光柱被挡（岩浆 / 水 / 玻璃不挡光），
  没有去反射信标内部字段，换版本或装别的信标增强模组也不会连带崩。
- 十件材料中**七件已是画师交付的正式贴图**（两张纸、两张邪笺、两瓶墨、空书卷，16×16 或 32×32），

  生成脚本 `design/make_materials_traced.py`：把参考图按整数倍缩回 16×16，按亮度分档映射到各物品的调色板，
  所以轮廓、明暗节奏与参考图完全一致。参考图：纸=原版纸、线=原版线、墨=铁魔法墨水、书卷=诡厄巫法道具。

### 七·五·二、属性乘区与 Curios 显示（2026-11-01 新增）

作者（m09952 / m10018）指出两点：**「属性提高 X%」不该走独立乘区**，以及**别的饰品都会在 Curios 的
「当装备在书籍栏：」里列出加成，我们的没有**。两条一起改，规则如下。

#### 乘区口径（唯一的规矩）

MC 1.20.1 的属性计算（`AttributeMap.calculateValue`）：

```
最终值 = (基础值 + Σ ADDITION) × (1 + Σ MULTIPLY_BASE) × Π (1 + MULTIPLY_TOTAL)
```

| 操作 | 语义 | 用在哪 |
| --- | --- | --- |
| `ADDITION` | 固定值相加（+7、+777） | 固定数值加成 |
| `MULTIPLY_BASE` | **乘法乘区**：多条之间相加，再整体乘一次 | **所有「提高 X%」的文本** |
| `MULTIPLY_TOTAL` | **独立乘区**：每条各自乘一次 | **只给材料档位**（`MaterialBonusHandler`） |

因此「攻击力提高 10%」= `MULTIPLY_BASE 0.10`，不是 `MULTIPLY_TOTAL`。
2026-11-01 一次性迁移（`grep MULTIPLY_TOTAL` 现在只剩 `MaterialBonusHandler` 与注释）：

| 文件 | 改动 |
| --- | --- |
| `ClassicBooksHandler` 的 `setModifier` | 查拉图斯特拉四项全改 `MULTIPLY_BASE` |
| `ClassicBookItem` | 理想国攻/血 +10%、神曲移速 +15% → `MULTIPLY_BASE` |
| `BookOfMeItem` / `BookOfMeHandler` | 移速 +30%、四项「翻倍」→ `MULTIPLY_BASE` |
| `CommandmentsHandler` | 12 条祝福/诅咒 → `MULTIPLY_BASE` |
| `CalamityDebuffManager` | 灾厄 −8% ×3 → `MULTIPLY_BASE` |
| `CovenantCodexHandler` / `ScriptureOfCovenantItem` | 攻/血 +77% → `MULTIPLY_BASE` |

#### Curios 显示：固定数值写在物品上

Curios 的 `CurioStacksHandler.update()` 里会调
`CuriosApi.getAttributeModifiers(slotContext, uuid, stack)` 拿到
`ICurioItem.getAttributeModifiers(...)` 的返回值，再用
`AttributeMap.addTransientAttributeModifiers(multimap)` 挂到佩戴者身上（卸下 / 换槽自动摘掉），
同时把这些修饰符渲染进 `curios.modifiers.<槽位>` 提示段。**写在物品上 = 能显示、也照样生效**。

| 饰品 | 显示来源 |
| --- | --- |
| 《空白的书页》 | `BlankPageItem.getAttributeModifiers`（移速 +10%、附魔数×0.5 血/攻、×0.25 幸运） |
| 《如我所书》 | `BookOfMeItem.getAttributeModifiers`（附魔数×1.0 血/攻、×0.5 幸运、移速 +30%） |
| 《理想国》/《神曲》 | `ClassicBookItem.getAttributeModifiers`（攻血 +10% / 移速 +15%） |
| 《圣约·原典》 | `ScriptureOfCovenantItem.getAttributeModifiers`（2026-11-01 从 handler 整体搬过来：777 护甲/幸运/攻击/韧性、免击退 1.0、移速 +0.0777、攻速 +7.77、交互距离 +7、攻血 +77%、可选暴击） |
| 《自然哲学的数学原理》 | `BookOfPrinciplesItem.getAttributeModifiers`（2026-11-01 改回真实数值：服务端读 `MiningProgressTracker`，客户端读 NBT 镜像；攻/甲 +等级、攻/甲 +5/15/25%、交互距离**只在挖矿满级时 +1**，低等级不挂修饰符） |
| 《翠玉录》 | `BookOfEmeraldTabletItem.getAttributeModifiers`（攻击 +`Config.tabletAttackBonus`；最大生命**没有基础值**，只有每解锁一种药水 +2） |
| 《十诫》 | **仍是 handler 按祝福条数动态算**，还没搬进物品（搬了才有 Curios 面板行），靠提示里的「当前加成」文字说明 |

#### 兜底层：`ProgressAttributeHandler` 的对账（2026-11-01）

`getAttributeModifiers` 只在**槽位内容变化**时被 Curios 调用，所以「等级涨了但面板/数值没变」是常态。
两本书现在同时：
1. 物品返回**当前真实数值** → 面板能显示、穿上那一刻就对；
2. `ProgressAttributeHandler` 每 10 tick 跑一次**对账**：缺了才补、数值或运算不同才先删后加、脱下就把三条/六条 UUID 全清掉，并把进度回写进物品 NBT（客户端镜像用）。

因为两边 UUID 完全一致，所以不会叠加；对账只修「丢了 / 旧了」，不做二次加成。

配套的两个语言键：

- `curios.identifier.book` = 「书籍」（槽位名）
- `curios.modifiers.book` = 「当装备在书籍栏：」（Curios 的属性段标题；不写就露生键）
- 我们自己那套材料加成区块的标题是「材料加成：」（`tooltip.yanscriptures.worn.head`），与上者区分开。

### 候选配方与上下小三角（2026-10-31 新增）

点一下换下一本书，同时把那一本还缺的下方材料列在成品名下面。
三格空着、或一本都对不上档位时，成品框显示「未选定配方」。

- 候选列表由 `BookWritingRecipes.matching(世界, 纸, 墨, 线)` 现算：**三格一放好就列出全部书写法**，
  按「纸档位 + 墨档位 + 线档位」从小到大排（《道德经》最便宜，排第一），不看材料池、也不看档位够不够。
  真写不写得成由 `BookWritingRecipes.canCraft(...)` 说了算（2026-10-31 修正：原先用 `findAll`，
  要求材料池里已经凑齐额外材料，导致「材料没齐就切不了书」）。
- 选中项存在方块实体的 `selectedIndex` 里，经 `ContainerData`（原版 data slot）同步给客户端，重登也记得住。
- 点箭头：客户端先本地挪一格（立刻有反馈），再发 `BookTableCyclePacket` 给服务端，服务端按**自己算的列表**挪，
  两边不会因为同步延迟算错。
- 成品名下面那行由 `BookWritingTableMenu.missing()`（→ `BookWritingRecipes.missing(...)`）给出：
  档位不够时直接报「该换成哪种纸/墨/线 ×几个」，份数不够时报还差几个，材料池里缺的额外材料一起列，
  红字「另需：羊皮纸 ×2、金胡萝卜 ×1」；全都够了改绿字「材料齐了 —— 空书卷右键台面上端即可写成」。
  这一行太长会截断成「…」，把鼠标停在成品框上能看到完整清单（悬浮提示里多一节「还缺这些材料」）。
- 配方需要额外材料（例如《道德经》要金胡萝卜、金苹果）时，这行只在**选中那一本**时算，切到别的书跟着变。
- 配方结构见 `BookWritingRecipe`（一条数据配方，JSON 在 `data/<命名空间>/recipes/book_writing/`）：
  `纸档位 + 纸数量 + 墨档位 + 墨数量 + 线档位 + 线数量 + 额外材料列表 + 成品`。
- 配方里写的是**档位**（Ⅰ~Ⅳ）而不是具体物品，所以高等级纸能写低等级的书；
  想加新材料只改标签 `#yanscriptures:papers / inks / threads`，不用改 Java。
- 写成后的提示语 `message.yanscriptures.book_table.crafted` 是 `§6写成了%1$s`（2026-11-01 按作者要求去掉句尾句号）——
  书名本身带书名号，所以文案里**不能**再加《》（2026-10-31 修正）；名字在 `Inventory#add` **之前**取好副本，
  否则背包放得下时物品被缩到 0 个，提示会变成「写成了空气」。
- **每写成一本，台面上那本《书与笔》随之消耗**（`BookWritingTableBlockEntity.consumeBook()`，2026-11-01 按作者要求）：
  书槽清空后要重新放一本才写得下一本，提示会变成「台面上得先放一本《书与笔》」。
- 不开游戏也能验证候选：服务器启动时 `RecipeAudit` 会打几行自查，例如
  `著书台候选自查：三格放好、材料池为空 → [dao_de_jing, republic, …]（10 条）`
  —— 三格放好就一定是 10 条（全部书写法），箭头一定出现；0 条说明三格里有空。

  ```json
    "type": "yanscriptures:book_writing",
    "paper":  { "tier": 1, "count": 2 },
    "ink":    { "tier": 1, "count": 1 },
    "thread": { "tier": 1, "count": 2 },

  ```

  额外属性随机——省得为了看一眼 Ⅳ/Ⅲ/Ⅲ 的属性去凑材料。

## 十一、底层机制说明

### 11.1 事件注册

所有处理器使用 `@Mod.EventBusSubscriber(bus = FORGE)` **自动注册**。
手工 `MinecraftForge.EVENT_BUS.register` 已全部移除——重复注册会让非幂等的数值改写执行两遍。

### 11.2 属性刷新的处理

Curios 的 `ICurioItem#getAttributeModifiers` 只在槽位变化时读取，因此改用品阶维持的**瞬时修改器**（tick-maintained transient modifiers）。

### 11.3 濒死保护的三层结构

| 层 | 机制 | 说明 |
|---|---|---|
| L2 | `LivingDeathEvent` 88% 取消 | 真死时记录时间戳 `BookOfMe_DeathAllowed` |
| L3 | 每 tick 巡检：生命 ≤0 且 `deathTime == 0` 时救回 | **最近 60 秒内真死过则完全避让**，避免死亡界面卡死 |
| 兜底 | 每 5 tick 补满血 | 应对绕过伤害管道的直接改血 |

### 11.4 反制定身
试炼/战斗中有模组会用持续改速度或改位置的方式「钉住」玩家。当前对策：

- 每 tick 清 `hurtMarked`（防击退覆盖移动输入）
- 检测「受伤中且 10 tick 内水平位移 < 0.05 格」→ 朝视线方向传送 1.2 格脱困

### 11.5 网络与界面

- `NetworkHandler`：自定义包（时停、状态记录等）
- `GuiHandler` / `EntityInfoOverlay`：覆盖层与信息显示
- `BookOfMeScrollHandler`：Shift + 滚轮翻页

### 11.6 抹除心智的实现

「2 秒内无法锁定目标」不是靠失明/虚弱这类效果冒充的，走的是事件拦截：

1. 受击瞬间清空攻击者的 `setTarget(null)` 与 `setLastHurtByMob(null)`
2. 在实体的持久化数据里写入到期时间 `YanMindEraseUntil`
3. `LivingChangeTargetEvent` 中，若当前时间未过到期时间 → 取消这次目标变更并再次清空目标

之所以不用 `setNoAi(true)`：那会把 Boss 的整套 AI 冻住，恢复时可能卡在某个阶段；
只拦「目标锁定」既能达成「失去敌意」的表现，又不破坏状态机。

### 11.7 随机头衔的实现

Goety 系 Boss 有一个公开字段 `titleNumber`（NBT 键同名）与配套的 `addTitleEffect()`。
生成后按**字段名**反射写入随机值并调用 `addTitleEffect()`：

- 有该字段的实体（使徒、异端教主等）自动获得随机头衔
- 没有该字段的实体（凋灵、寒冰隐士）静默跳过
- 好处是不写死类名，其它实现同一约定的模组也会被覆盖

### 11.8 四个「框架细节」踩坑记录

这些都不是业务逻辑错误，而是对框架行为的误判。记下来避免重复踩。

| 坑 | 表现 | 真相 |
|---|---|---|
| **取消事件不再派发** | 打训练假人有伤害但不显示 DPS | Forge 默认跳过「已被取消的事件」，监听器必须写 `receiveCanceled = true` |
| **`AABB(Vec3, Vec3)` 不排序** | 准星朝 -X/-Z 时永远找不到实体 | 该构造直接把两个点当 min/max，必须手动取 `Math.min/max` |
| **Curios 不同步手改的 NBT** | 血条与 DPS 一直不刷新 | 直接改 `stack.getOrCreateTag()` 不经过 `setStackInSlot`，Curios 认为没变化 |
| **自定义实体必须有渲染器** | 试炼一启动客户端就崩（`EntityRenderDispatcher` 空指针） | 即使是纯逻辑、不可见的实体，也要注册 `NoopRenderer` |

### 11.9 Goety 仪式字段的真实单位

从 `DarkAltarBlockEntity` 字节码确认：

```java
if (level.getGameTime() % 20 == 0) {        // 每秒一次
    if (souls >= recipe.getSoulCost()) {
        cage.decreaseSouls(recipe.getSoulCost());   // soulCost = 每秒消耗
        this.currentTime++;                          // duration 以「秒」计
    }
}
```

- `soulCost`：**每秒**灵魂消耗，不是总量
- `duration`：**秒**，不是刻

### 11.10 处理器之间的隐形冲突

《如我所书》的 tick 对**所有玩家**每 tick 执行；在「没戴书」分支里会把 `mayfly` / `flying` 置为 false 并同步。于是只戴圣约时，飞行被它每 tick 关闭一次。

**教训**：写「佩戴时生效」的逻辑，一定要检查同一个类里有没有「未佩戴时撤销」的分支会影响其它装备。

### 11.11 时停的正确实现

- 计时用 `level.getGameTime()`，不用 `System.currentTimeMillis()`
- 记录每个实体**原本的** `isNoGravity()`，结束时按原值还原（否则全场永久悬浮）
- 冻结一切非玩家实体，跳过其它玩家
- 被冻住的实体**不能造成伤害**（在 `LivingHurtEvent` 入口按来源判定取消）

### 11.12 不可摧毁的训练假人

铁傀儡 + 四层保护：

1. `LivingHurtEvent` HIGHEST 取消（保留金额，供 DPS 统计读取）
2. `LivingDeathEvent` HIGHEST 取消 + `revive()`
3. 每 tick 清无敌帧、回满血、清火焰
4. 审判控制器遇到假人只走普通伤害，不做强制 `setHealth`

> 为什么不用僵尸：雷击会把僵尸替换成别的实体，标签丢失后所有保护失效。

**怎么移除（2026-10-30 改）**：`/ys debug dummy clear [range]` 直接 `Entity#discard()`，
而不是 `/kill`。区别在于 discard 只是把实体从世界里摘掉并给客户端发移除包——
不放死亡音效、不掉落、不派发 `LivingDeathEvent`、不触发任何「死亡后」逻辑，
也就不会撞上假人自己的「拦截死亡」那层保护；写进存档的实体同样被删掉，重进世界不会再冒出来。
`/kill @e[tag=YanTrainingDummy]` 仍然可用（`generic_kill` 是显式放行的例外），
但会走一遍死亡流程，测完清理用 clear 更干净。

### 11.13 本地模组依赖的正确接法（libs → libs-m2）

开发环境离线，模组 jar 只能手工放进 `libs/`。但**直接丢文件不会生效**：

1. `runtimeOnly files(fileTree(dir: 'libs'))` 会被 ForgeGradle 拒绝——`files(...)` 依赖不做重映射，
   jar 以 SRG 混淆名进运行时，启动时报 `NoSuchMethodError`；
2. 正确做法是 `design/make_local_m2.py` 把 jar 按 Modrinth 的目录布局复制进 `libs-m2/maven`
   （生成最小 POM、groupId 固定 `maven.modrinth`），`build.gradle` 用与在线方案**完全相同**的坐标
   引用，`fg.deobf` 才会重映射。

`make_local_m2.py` 的 `ITEMS` 是唯一清单，新增模组要同时改这里和 `build.gradle`：

| 模组 | 坐标 | 谁需要 |
|---|---|---|
| curios-forge | `maven.modrinth:curios-forge:5.14.1-1.20.1` | compileOnly + runtimeOnly |
| jei | `maven.modrinth:jei:15.74.0.229` | compileOnly（写插件）+ runtimeOnly（看配方页） |
| jade | `maven.modrinth:jade:11.13.3` | 只 runtimeOnly（不写插件） |

三个坑：

- **版本号里的 `+`**：Curios 的 jar 叫 `5.14.1+1.20.1`，但 Gradle 会把带 `+` 的版本当动态版本，
  所以本地仓库改成 `5.14.1-1.20.1`（POM 与坐标必须一致）。
- **Curios 的 API**：主 jar 里已经含 `top/theillusivec4/curios/api/*`，不必再引 `:api` 分类器，
  原先的在线坐标 `top.theillusivec4.curios` 已删除，避免运行时出现两份 Curios。
- **假人（dummmmmmy）**：jar 里缺 refmap，mixin 目标写死 SRG 名 `m_6475_`，在 official 映射下必然
  `InvalidInjectionException`，已从 `ITEMS` 移除（jar 留在 `libs/` 当资料）。

验证：`./gradlew compileJava --offline` 通过，且
`./gradlew dependencies --configuration runtimeClasspath` 里每个模组只有一条解析结果。

### 11.15 同一份事实一 tick 只算一次（2026-10-30 定）

**问题**：九本书那套逻辑一个 tick 里会问七次「戴着哪本」，旧 `wears()` 每问一次都
遍历整张饰品栏（每个槽位组 → 每一格）。一本书一 tick 七次，二十个玩家就是上百次全量遍历。
查询本身不重，重复得没有必要；而且这个模式会被后面新加的书继续复制。

**改法（不移动任何玩法逻辑，只去掉重复计算）**：

| 位置 | 以前 | 现在 |
|---|---|---|
| 佩戴查询 | 每次 `wears()` 遍历 Curios | `WornCache.refresh(player)` 每 tick 扫一次，`wears()` 变成查表；缓存未命中会现场扫一次兜底 |
| 属性修正器 | 每 tick `removeModifier` + `addTransientModifier` | `applyModifier()`：已经是目标值就什么都不做 |
| 影子找本体 | 64 格内 `getEntitiesOfClass` | `ServerLevel#getEntity(UUID)`（哈希查找）+ `SHADOW_BY_TARGET` 去重表 |
| 玩家下线清理 | `SessionCleanup` 里手写三行 | 注册表：各处理器静态块里 `register(...)` 一行，`SessionCleanup` 不再被改 |

**约定**：以后任何「按玩家 UUID 记账」的新类，都在自己的静态块里写
`SessionCleanup.register(MyHandler::cleanupPlayer)`，并保证清理器能容忍「本来就没有数据」。
新增九本书之外的佩戴判定，一律走 `WornCache.wears(...)`，不要再自己遍历 Curios。

### 11.14 配方一敲定就必须在 JEI 里看得到（2026-10-30 定）

约定：**任何配方在被定为「定稿」的那一刻，就要在 JEI 里能查到**，不等美术、不等平衡。
实现上不用每加一条就写一次 JEI 代码 —— JEI 侧只有三条通道：

| 配方种类 | 写在哪里 | JEI 怎么收录 |
|---|---|---|
| 工作台 / 熔炉等原版配方（空书卷、著书笔、方块与和平、如我所书…；**书类不放这里**） | `data/yanscriptures/recipes/*.json` | JEI 直接读原版配方表，**自动**收录，无需代码 |
| 炼药锅投料（草纸 / 羊皮纸 / 至邪之笺 / 墨水 / 血墨 / 不洁之墨 / 麻绳 / 龙筋 / 金绳 / 《翠玉录》） | `data/yanscriptures/cauldron/*.json` | `compat/JeiCompat.java` 读 `CauldronRecipes.all()` 登记到 `yanscriptures:cauldron` 分类，**自动**收录 |
| 著书台（纸 + 墨 + 线，各带数量，可另加材料池里的额外材料 → 一本书） | `data/yanscriptures/recipes/book_writing/*.json`（`yanscriptures:book_writing`） | `compat/BookWritingRecipeCategory.java` 读世界配方表，**自动**收录（KubeJS 加的也会出现） |

也就是说：以后加一条配方，只要选对通道并写进对应位置，JEI 会自动出现，
不需要再改 `JeiCompat`。唯一要注意的是**数据包写错会静默少一条**，
所以加了启动自查：

`src/main/java/com/example/examplemod/RecipeAudit.java` 在 `ServerStartedEvent` 打一行 INFO：

```
配方自查：工作台/原版 5 条 [yanscriptures:blank_page, yanscriptures:blank_scroll,
yanscriptures:writing_quill, yanscriptures:book_of_peace, yanscriptures:book_of_me]，
炼药锅 10 条，著书台 10 条，锻造台换料 1 条
```

数字掉了 = 对应 JSON 解析失败或被误删；全为 0 会额外打 WARN。

另有一类不算配方但同样要进 JEI 的：**获取方式的说明**。十张残卷、四件史诗
用 `addItemStackInfo` 写了「信息」页（见 §13.1 / §13.2），以后新增这种「只能靠条件拿」的
物品，也按同样方式补一条信息页。

### 11.15 tooltip 文案规范（2026-11-05 作者定）

作者把「哪些底层机制该写、哪些不该写」的判决落在了物品提示上，约定如下：

| 规则 | 具体做法 |
|---|---|
| 提示框只写**玩家能感知的行为** | 「无敌帧」「最终伤害」「乘区」「事件」「NBT」「标签」「判定点积」一律不写；精确数值留给 JEI 信息页（`jei.yanscriptures.book.<id>.detail.N`） |
| 术语固定三组 | 攻击力（不写「攻击伤害」）、生命上限（不写「最大生命值」）、移动速度（不写「移速」） |
| 减号只用 ASCII `-` | 不用 U+2212 `−` |
| 时间单位 | 60 秒以内写「秒」，600 秒这类写「10 分钟」；不写 `10s` |
| 组合键统一写法 | `Shift + T`、`Shift + 右键`（不再出现 `Shift+T`、`按住 [Shift]`） |
| 按键提示走 keybind | 需要提示按键时传 `KeyMapping#getTranslatedKeyMessage()`，不写死「按 V 键」 |
| 材质档位行 | 「制书材料加成：」+「材料：纸 Ⅱ · 墨 Ⅰ · 装订 Ⅲ」（「线」改称「装订」） |
| 不重复 Curios 已给的信息 | 不写「槽位：书」，Curios 会自己生成「当装备在书籍栏：」 |
| `%%` 只在**传参**的键里用 | 无参数的 `Component.translatable(key)` 不格式化，写 `%%` 会原样显示成两个百分号 |

被判「保留原样」的：`全属性（三条相加）`、`槽位：书`、`已记录附魔：%s / 093`、以及
《孙子兵法》《物种起源》《几何原本》《梦的解析》《天工开物》《理想国》里被作者勾选为
「不改」的机制句。

> **名著的机制说明也走这条路**（2026-11-02 起）：`registerBookDetailInfo` 遍历
> `ExampleMod.CLASSIC_BOOKS`，页头固定两行「怎么用」+ `effect1/effect2`，正文按
> `jei.yanscriptures.book.<id>.detail.N` 从 1 连续读到缺键为止。
> **加一本新书只要补 lang 键 `detail.1..N`，不用动 Java**；漏写则这一页只有页头，
> 不会露出生键名。18 本（第一批 9 + 第二批 9）都已补齐，其中《易经》按六卦逐条写数值。

> 信息页的取舍（2026-10-31 作者 m08693 + m08876）：**写「获取条件」或「用途」，不写合成方式**
> ——合成方式按 `R` 就有，重复一遍反而淹掉真正需要的字。九本名著那三条「现在有哪几本 /
> 还不能合成」的清单已删；空书卷、著书笔改回**用途**说明：著书笔是「把讲台改成著书台」，
> 空书卷写两条 —— ①放著书台上写书；②在锻造台上当模板，配合一本书与纸/墨/线换料升档（模板消耗）。

### 11.16 属性加成写在物品侧，不写在 Handler 里（2026-11-07 作者定）

作者原话：「以后任何无条件的属性加减，还有像史记那样子的成长型的固定数值加减，都写成，
curios 的佩戴在某某，加多少加多少，那样子，就是之前改的那种」。

| 类型 | 写在哪 | 例子 |
|---|---|---|
| **无条件**（戴着就是这么多） | 物品侧 `ICurioItem#getAttributeModifiers`，Curios 自动列成「当装备在书籍栏：」 | 《理想国》攻/血 +10%、神曲移速 +15%、圣约 777、《翠玉录》《原理》的静态部分 |
| **成长型的固定数值**（数值会变，但变的是「固定加多少」，不依赖当下状态） | 同上；进度存在**物品自己的 NBT** 里，改完调 `ICurioStacksHandler#update()` 让 Curios 重算 | 《史记》每个进度 +0.5% 暴击率 / +1% 暴击伤害 / +0.5 幸运 |
| **有条件的、跟状态走的** | Handler 里用 `BookAttr.set(...)` 每刻/每次事件算 | 罪孽层数、浮士德契约、易经六卦、伊利亚特单挑/围攻、君主论血量阈值、三十六计隐身、君主论光环（挂在仆从身上） |

为什么：①玩家能直接在饰品栏看到「加多少」，不用读 tooltip 猜；②这些修饰符由 Curios 负责
挂/摘，不会出现「书取下来了加成还在」这类漏删；③Handler 里挂的东西一旦忘了清理就是永久脏数据。

坑：①`getAttributeModifiers` 里拿不到玩家、只能读 `ItemStack`，所以成长型必须把进度写进物品 NBT；
②改完 NBT 不调 `update()` 的话 Curios 不会重读，面板数字会停在旧值；③别家模组的属性
（`l2damagetracker:crit_rate` 等）可能查不到，传 null 进来要静默跳过，不能整件失效；
④物品侧返回的修饰符**不要**和 Handler 里同 UUID 的修饰符并存，否则就是两个来源互相打架。
>

> **寂灭之笺**（用途 = Ⅳ 档纸，著书台与锻造台都可用；来源 = 至邪之笺丢进岩浆、竖列下方有已点亮

### 13.3 两段式发放：先「就绪」，再「违逆」

这是整套系统里唯一不直观的地方，也是刻意设计：

1. **条件达成时只写「就绪」标记**（NBT `MsR_<id>`），不立刻给物品；
2. 后台每 20 刻扫一次就绪队列，十张残卷**额外要求**玩家戴着《圣典·戒律》且该诫的 `Curse_N` 为真（即已经「违逆」过那一条诫命）才真正发放；
3. 发放成功同时写完成标记（`MsD_<id>`），发不进背包就原地掉落。

于是残卷的叙事成立：**先看见自己的罪，才拿得到那一卷**。史诗没有这层门槛，就绪即发。

就绪期间玩家会收到一行灰字提示（`message.yanscriptures.milestone.pending`），说明还差「违逆」这一步。

### 13.4 三条判定规则

| 规则 | 实现 |
|---|---|
| **「一场战斗」** | 造成或受到伤害都把窗口续到「现在 + 100 刻（5 秒）」；窗口开启时记基线，连续 5 秒无伤害交互 / 死亡 / 退出即结算。打一下就跑不累计 |
| **「首领」** | `minecraft:ender_dragon`/`wither`/`warden` 直接列表命中；其它模组的首领看实体类型标签 `#forge:bosses`、`#c:bosses`、`#yanscriptures:bosses`。**不按生命值判定**——装了很多模组后普通怪血量也会暴涨 |
| **「独一」的豁免表** | 开局绑定诅咒饰品与其反转道具不算违规，写在 `CurioExemption` 里（七咒之戒、灾厄之册、七块刻蚀板等 9 件）。没有这张表，玩家为了反转灾厄之册就会先把第一诫的诅咒拉满 |

### 13.5 `/ys milestone selftest` 怎么用

十四条条件的真实触发大多要几小时，所以做了一个「伪造前置 → 跑真实监听器 → 看标记」的自检：

```
/ys milestone selftest
```

它一次跑完全部 14 条（不支持只跑某一条，也**尚未覆盖**九本名著的 9 条）。每条都会构造真实的 `LivingHurtEvent` / `LivingDeathEvent` / `LivingHealEvent` 等事件并直接 `post` 到事件总线，走的是和实战完全相同的处理路径——业务逻辑、阈值比较、豁免表、首领判定都会被验证到，唯一没被验证的是「原版在什么时机派发这个事件」。

输出为逐条 `§a通过` / `§c失败`，末尾给汇总。跑完建议 `/ys milestone reset` 清掉测试产生的标记。

### 7.6.2 《神曲》的落点必须先加载区块（2026-10-30 记录）

没去过的维度里区块根本没加载，`level.getHeight(Heightmap...)` 在未加载区块上只会返回
`minY`，于是「永远找不到落脚点」。现在的流程：

1. 以该维度 `getSharedSpawnPos()` 为中心、±2000 格内随机取点；
2. **第一段只挑已经加载的区块**（`level.hasChunk(...)`），这一步不生成任何东西，
   不花钱；
3. 第二段才允许**最多同步生成 `SPOT_MAX_SYNC_GENERATE = 1` 个区块**
   （`level.getChunk(x >> 4, z >> 4, ChunkStatus.FULL, true)`）；
4. 每取到一个点，自己从世界顶端往下扫整列，找「脚下实心 + 两格空气 + 无流体」的位置
   （heightmap 只看表面，遇到洞穴、水下、基岩顶都会误判）；
5. 全都没命中（虚空 / 纯水 / 熔岩海）才走兜底：在维度出生点铺一块 3×3 圆石落脚石，
   并给玩家一句「已为你铺了一块落脚石」。

> **为什么不能「只认已加载区块」**（2026-10-30 第二轮审查的建议）：玩家没去过的维度
> 一个区块都没加载，那样会退回「永远找不到落脚点」的老 bug。
>
> **为什么也不能无条件生成**：同步生成一整块（10~100 ms）发生在服务端主线程，
> 以前 24 次采样每次都生成，最坏能卡两秒以上，多人服务器会直接踢人。
> 折中就是「已加载优先 + 只额外生成一块 + 实在不行铺落脚石」。

### 7.6.1 两个实现坑（2026-10-30 记录）

**《道德经》的空血不能写成真 0 血。** 把服务端生命设成 `0.0f` 时，客户端收到的血量也是 0，
于是弹死亡界面；而服务端的 `LivingDeathEvent` 又被我们取消了，两边状态不一致，就出现
「原地复活、周围怪物不同步、什么都点不动，重连才好」。现在空血用 **0.5 点生命**当地板
（`ClassicBooksHandler.DAO_HEALTH_FLOOR`）：血条看着是空的，但玩家确实活着。
另外「真死」那一下会先写 `DaoDying` 标记，避免被自己的空血逻辑再接管一次；
`PlayerEvent.Clone` / `PlayerRespawnEvent` 里清空 `DaoEmpty/DaoStart/DaoAmp/DaoDying`。

**《百年孤独》的“看不见”不能调 `List.clear()`。** `ItemTooltipEvent.getToolTip()` 是原版
同一个列表，创造模式背包在渲染时会往这个列表 `add(1, ...)`；一旦被清成 0 长度就直接抛
`IndexOutOfBoundsException: Index: 1, Size: 0`（`crash-2026-10-30_00.51.28-client.txt`）。
现在改成把每一行替换成空串、并保证至少 2 行。

> 设计上刻意让九条各自落在不同的玩法面上：残血（道德经）、洞穴（理想国）、
> 垂直探索（查拉图斯特拉）、跨维度（神曲）、坐骑（堂吉诃德）、单人（百年孤独）、
> 静止（几何原本）、承伤（物种起源 / 九章算术）。这样九本书不会都变成「多打几只怪」。
